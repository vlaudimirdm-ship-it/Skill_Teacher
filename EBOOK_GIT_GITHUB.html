Capítulo 1: Desmistificando Git vs GitHub

1.1 A Confusão Mais Comum da Tecnologia

Para quem está começando, Git e GitHub parecem a mesma coisa. Mas confundi-los é como confundir o carro com a garagem ou uma câmera fotográfica com o Instagram.

📸 A Analogia da Fotografia:
  • O Git é a Câmera Profissional: Funciona 100% offline. Você tira as fotos (commits), salva no seu próprio cartão de memória (disco rígido) e controla seu acervo sem precisar de internet.
  • O GitHub é a Galeria na Nuvem / Rede Social: É o site onde você sobe as fotos da sua câmera para compartilhar com a equipe, expor seu trabalho, fazer backup seguro e receber comentários.

1.2 O que é o Git?

O Git é um sistema de controle de versão distribuído criado em 2005 por Linus Torvalds. Sua principal função é atuar como uma máquina do tempo para arquivos de texto e código. Ele não "roda" seus programas; ele vigia e registra minuciosamente o que mudou, quem mudou, quando mudou e por que mudou.

1.3 O que é o GitHub?

O GitHub é uma plataforma de hospedagem em nuvem que utiliza o Git por trás dos panos. Além de guardar seu código com segurança em servidores globais, ele adiciona uma camada gráfica rica de colaboração: acompanhamento de tarefas (Issues), revisão de código (Pull Requests), automações (GitHub Actions) e páginas públicas (GitHub Pages).

Capítulo 2: Configuração e Identidade Global

2.1 Por que o Git exige que você assine seus trabalhos?

Em um projeto profissional com 10 ou 100 colaboradores, o Git precisa saber exatamente quem escreveu cada linha de código. Se um erro for introduzido ou uma funcionalidade incrível for criada, o sistema precisa associar essa autoria a um nome e a um e-mail válidos.

2.2 Os Comandos de Identidade

Antes de fazer o primeiro commit em qualquer computador novo, configuramos nossa identidade global:

# 1. Configurar o seu nome público de autor
git config --global user.name "Vlaudimir Marques"

# 2. Configurar o seu e-mail (o mesmo vinculado à sua conta do GitHub)
git config --global user.email "vlaudimirdm@gmail.com"

# 3. Conferir se tudo foi gravado corretamente
git config --list
💡 Dica de Ouro: A flag --global significa que essas informações valerão para todos os repositórios que você criar neste computador. Se em algum projeto específico da empresa você precisar usar um e-mail corporativo diferente, basta rodar o mesmo comando dentro da pasta do projeto sem a palavra --global.

Capítulo 3: A Santa Trindade dos 3 Estados

3.1 Como o Git Enxerga o Seu Projeto

Diferente de um arquivo salvo no Word ou no Google Docs (onde você digita e tudo é salvo na mesma hora), o Git possui um processo deliberado em três etapas. Ele nunca grava nada de surpresa:

🎭 A Analogia do Teatro e da Foto Oficial:
  1. Working Directory (Os Bastidores / Camarim): É a sua pasta de trabalho normal no computador. Você edita, cria e deleta arquivos. O Git sabe que algo mudou, mas nada está preparado ainda. (No terminal, esses arquivos aparecem em VERMELHO).
  2. Staging Area (O Palco da Foto): Você chama para o palco apenas os atores (arquivos) que devem sair na foto oficial agora. (No terminal, esses arquivos aparecem em VERDE após o comando git add).
  3. Repository (O Álbum de Família Oficial): Você clica na câmera fotográfica. O Git tira a foto dos arquivos que estavam no palco e registra para sempre na linha do tempo com uma mensagem explicativa (git commit).

3.2 Os Comandos Fundamentais

# Inicializar o repositório na pasta atual
git init

# Checar o painel de bordo a qualquer momento
git status

# Enviar um arquivo específico para o palco (Staging)
git add ideias.txt

# Enviar TODOS os arquivos modificados para o palco
git add .

# Tirar a foto oficial com uma mensagem descritiva
git commit -m "feat: primeiro commit oficial do projeto"

3.3 Superando o Editor Vim no Terminal

Se por acidente você esquecer a flag -m "mensagem" e digitar apenas git commit, o Git abrirá um editor dentro do terminal (frequentemente o clássico Vim).

Para sair dele sem desespero: 1. Aperte a tecla Esc; 2. Digite :wq (que significa Write and Quit / Salvar e Sair); 3. Aperte Enter!

Capítulo 4: A Máquina do Tempo (log e diff)

4.1 Inspecionando o Passado: O Histórico

Como navegar pela linha do tempo para ver o que já foi construído? Usamos a família de comandos git log: 

# Visualização resumida e elegante (uma linha por commit)
git log --oneline

3bf24f2 Merge pull request #1 from vlaudimirdm-ship-it/feat-ideia-projeto
37211f6 feat: adiciona propostas de projetos praticos
e9c9da7 docs: atualiza registro da aula 07 no template de progresso
8c9c003 feat: adiciona anotacoes na branch de teste
cdb6cef Primeiro commit
🔑 O que são os códigos estranhos (ex: 3bf24f2)? Eles são chamados de Hashes SHA-1. Cada commit recebe uma impressão digital matemática única no universo. Com esse código de 7 caracteres, você pode apontar para aquele momento exato da história e inspecionar ou restaurar arquivos como estavam naquele segundo.

4.2 Enxergando Linha por Linha com git diff

Enquanto o git status apenas te dá o "índice" de quais arquivos foram tocados, o git diff abre o microscópio e revela as entranhas da alteração:

  • Linhas iniciadas com + (verde): foram adicionadas;
  • Linhas iniciadas com - (vermelho): foram deletadas ou substituídas.

Capítulo 5: O Guarda-Costas do Projeto (.gitignore)

5.1 O Perigo de Versionar Arquivos Indesejados

Em qualquer sistema operacional, existem arquivos temporários que não fazem parte do seu trabalho. No Mac, por exemplo, o sistema cria silenciosamente arquivos chamados .DS_Store em todas as pastas para guardar ícones e posições de janelas. Em projetos de programação, existem pastas pesadíssimas como node_modules/ ou senhas gravadas em arquivos .env.

Se você comitar esses arquivos e enviar para a nuvem, você pode travar o repositório ou vazar credenciais sigilosas!

5.2 Como Funciona o .gitignore

O .gitignore é um arquivo de texto simples colocado na raiz do seu projeto. Cada linha dele é uma ordem expressa para o Git: "Finja que esses arquivos não existem!". 

# Exemplo de conteúdo de um .gitignore
.DS_Store          # Ignora lixo de sistema do macOS
*.log              # Ignora qualquer arquivo que termine com .log
senhas.txt         # Ignora arquivos com chaves confidenciais
node_modules/      # Ignora pastas inteiras de bibliotecas
⚠️ Regra Crítica: Crie o .gitignore no início do projeto! Se você já tiver commitado um arquivo antes de colocá-lo no .gitignore, o Git continuará rastreando-o até que você o remova explicitamente do índice.

Capítulo 6: Conectando com a Nuvem (Push Remoto)

6.1 O Conceito de Repositório Remoto (Remote)

Até a Aula 05, seu projeto existia exclusivamente dentro do seu Mac. Para levá-lo ao GitHub, precisamos criar uma "ponte" entre o seu computador e o servidor na nuvem. Essa ponte se chama Remote.

Por convenção universal, o servidor principal recebe o apelido carinhoso de origin.

6.2 Os Comandos de Conexão e Envio

# 1. Vincular a pasta local ao endereço do repositório no GitHub
git remote add origin https://github.com/vlaudimirdm-ship-it/Skill_Teacher.git

# 2. Conferir se a conexão está apontando para o lugar certo
git remote -v

# 3. Fazer o primeiro envio e configurar o rastreamento automático
git push -u origin main
💡 O que significa a flag -u? Significa Upstream (Rastreamento). Ela cria um fio invisível dizendo: "A partir de hoje, a branch main deste Mac conversa diretamente com a branch main lá do GitHub origin". Nas próximas vezes, basta você digitar simplesmente git push!

Capítulo 7: Linhas do Tempo Paralelas (Branches)

7.1 O que é uma Branch?

A palavra Branch significa Galho ou Ramificação. Ela é a capacidade do Git de clonar a linha do tempo para que você trabalhe em uma cópia paralela e segura sem encostar na versão oficial (main).

📄 A Analogia do Cardápio do Restaurante:
  • A main é o Cardápio Oficial: Está impresso e nas mãos dos clientes. Não se deve rabiscar ou fazer testes nele.
  • A branch é a Xerox de Rascunho: Você tira uma xerox do cardápio e vai para os fundos da cozinha testar receitas novas. Se der errado, joga no lixo. Se der certo, copia para o cardápio oficial!

7.2 Branch vs Ambiente Virtual: Uma Distinção Vital

Muitos profissionais confundem esses dois conceitos porque ambos usam o verbo "isolar":

  • Branch do Git: Isola o TEXTO e o CÓDIGO dos arquivos.
  • Ambiente Virtual (ex: venv do Python, Docker): Isola os PROGRAMAS e BIBLIOTECAS instalados no computador.

7.3 O Ciclo Local de Branches

# Listar as branches existentes
git branch

# Criar uma branch nova e já entrar nela (-c de create)
git switch -c teste-ideias

# Voltar em segurança para a branch principal
git switch main

# Trazer as novidades da branch paralela para a main (Merge)
git merge teste-ideias

Capítulo 8: Trabalho em Equipe Profissional (Pull Requests)

8.1 Por que Equipes não Fazem Merge Direto na Main?

Em um projeto individual, fazer git merge na sua máquina e dar git push funciona. Mas em equipes de tecnologia, isso geraria um atropelamento de trens: alguém subiria código com bug que derrubaria o sistema para todos os outros colegas.

A solução universal da indústria é o Pull Request (PR).

8.2 O que é o Pull Request (PR)?

Traduzindo ao pé da letra: "Pedido formal para puxar". É quando você diz ao seu time: "Pessoal, criei este galho isolado na nuvem. Revisem minhas alterações. Se estiver tudo aprovado, puxem para a main!".

8.3 O Ciclo Completo de Colaboração (O que fizemos na Aula 08)

# 1. No Mac: Criar a branch de funcionalidade
git switch -c feat-ideia-projeto

# 2. No Mac: Fazer a melhoria e comitar na branch
git add ideias.txt
git commit -m "feat: adiciona propostas de projetos praticos"

# 3. Enviar APENAS o galho para o GitHub (sem tocar na main)
git push -u origin feat-ideia-projeto

# 4. Na Web (GitHub): Abrir o Pull Request #1 e clicar em "Merge pull request"

# 5. No Mac: Voltar para a main
git switch main

# 6. No Mac: PUXAR as novidades da nuvem para o seu computador!
git pull origin main

# 7. No Mac: Deletar o galho que já foi incorporado
git branch -d feat-ideia-projeto
📦 Mnemônico da Caixa (Nunca mais confunda Push e Pull):
  • PUSH (Empurrar): Você empurra a caixa de alterações do seu Mac para cima da estante (GitHub).
  • PULL (Puxar): Você puxa a caixa de alterações de cima da estante (GitHub) para o seu Mac.

Capítulo 9: Segurança, No-Code e Prevenção de Malware

9.1 O Dilema de Segurança no Mundo No-Code

Se você trabalha com ferramentas No-Code, automações ou está iniciando em programação, pode surgir a dúvida: "Como me protejo se alguém tentar mandar um código malicioso ou vírus disfarçado de contribuição no GitHub?".

🛡️ A Chave do Castelo é Sempre Sua: No Git e GitHub, ninguém tem o poder de injetar código na sua versão oficial sem que você clique voluntariamente em autorizar. O código de terceiros fica em quarentena na aba do Pull Request aguardando seu veredito.

9.2 Os 4 Sinais Vermelhos na Aba *Files Changed*

Antes de clicar em Merge em qualquer contribuição de terceiros, abra a aba Files changed e observe:

  • Arquivos Executáveis ou Ocultos: Desconfie na hora se o PR adicionou arquivos como .exe, .bat, .sh, .bin ou arquivos zipados. Projetos colaborativos normais só compartilham código-fonte legível.
  • Scripts que Baixam Coisas da Internet: Verifique se há comandos tentando fazer download silencioso de URLs desconhecidas.
  • Typosquatting de Bibliotecas: Preste atenção em nomes de pacotes adicionados que imitam bibliotecas famosas com erros sutis de digitação (ex: requsets em vez de requests).
  • Código Ilegível / Ofuscado: Blocos de texto que parecem códigos criptografados sem explicação lógica são clássicos de injeção maliciosa.

9.3 A IA como sua Perita de Segurança

Não precisa ser um hacker para se defender. Você pode simplesmente copiar o código que a pessoa sugeriu na aba Files changed, abrir sua IA de confiança e pedir:

"Analise esse código que recebi em um Pull Request. Há alguma tentativa de roubo de senhas, instalação de vírus, comandos de terminal perigosos ou vulnerabilidades aqui?"

Capítulo 10: O Guia Rápido de Bolso (Cheat Sheet)

Guarde esta tabela. Ela contém os comandos essenciais na ordem em que você os utilizará no seu dia a dia profissional:

Comando Git O que ele faz? Quando utilizar?
git status Mostra o estado atual dos arquivos A qualquer momento, para saber o que está modificado ou pronto.
git diff Mostra as linhas exatas adicionadas e removidas Antes de comitar, para revisar o que você realmente alterou.
git add <arquivo> Move o arquivo para o palco (Staging) Quando você preparou uma alteração e quer incluí-la no commit.
git commit -m "msg" Grava a foto oficial permanente no histórico Sempre que concluir uma pequena unidade lógica de trabalho.
git log --oneline Exibe a linha do tempo resumida dos commits Para auditar o histórico e ver os identificadores (hashes).
git switch -c <nome> Cria um galho novo e já pula para dentro dele Sempre antes de começar a programar uma ideia ou funcionalidade.
git switch <nome> Alterna entre galhos existentes Para voltar para a main ou inspecionar outra branch.
git push -u origin <branch> Publica a branch isolada no GitHub Quando você terminar a tarefa e quiser abrir um Pull Request.
git pull origin main Puxa as novidades da nuvem para o Mac Depois de aprovar um PR no GitHub ou ao iniciar o dia de trabalho.
git branch -d <nome> Deleta o galho local com segurança Depois que o merge já tiver sido concluído e sincronizado.

O Que Nos Espera: O Conflito de Merge!

Até agora, todas as fusões que realizamos foram suaves e automáticas (o chamado Fast-Forward ou merge limpo do GitHub). Isso aconteceu porque ninguém mexeu na mesma linha que você ao mesmo tempo.

Mas o que acontece quando:

  • O Desenvolvedor A altera a linha 5 do arquivo para dizer: "Cor de fundo: Azul";
  • E simultaneamente o Desenvolvedor B altera a mesma linha 5 para dizer: "Cor de fundo: Verde"?

O Git não é adivinho. Ele não pode chutar qual das duas ideias é a correta. Ele para o processo, levanta uma bandeira e diz: CONFLITO DE MERGE!

Na Aula 09, vamos provocar um conflito intencional de merge, inspecionar os marcadores de conflito (<<<<<<<, =======, >>>>>>>) e aprender a resolvê-lo com calma, elegância e segurança profissional.
